## Acceptance plan

1. **Freeze code/evidence lineage:** record the SDK commit, Rust toolchain, `Cargo.lock`, fixture version, seed, CI run ID, and result artifacts. Do not reuse the paper's historical test counts or 64,152 decisions without original input manifests and logs.
2. **Verify G2a and G2b separately:** a tool's presence in discovery differs from callback authorization. The protected-tool step-up regression exercises both within a single real runtime, including policy recovery.
3. **Classify audit scope:** transitions, intervention requests, failed commits, host observations and execution receipts are distinct event types and cannot be described as one complete in-memory log.
4. **Stress the boundary:** adversarial stale catalogs, permissions, approval replay, session mixups, invalid arguments, failures, time rollback, parallel calls and ungoverned alternate routes. Existing suites cover a subset; evaluate actual production integration separately.
5. **Cross-validate policy appropriateness:** independent judgments and matched task outcomes are needed before claiming that any acoustic restriction is appropriate. This is not an E1 software invariant.

## Publication-safe interpretation

E1 can support **conformance of the implementation to explicitly scoped policy contracts** in tested environments. It does not establish emotion recognition, empathy, general-purpose agent safety, or task-value improvement. For the IEEE Access manuscript, put conformance and integration results in Section IV (Solution, Technical Validation) and keep unmeasured human utility in Limitations / future evaluation.
